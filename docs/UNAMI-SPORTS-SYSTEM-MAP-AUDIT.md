# Unami Sports — Full System Map and Implementation Audit

**Audit basis:** repository implementation at the time of inspection

**Purpose:** establish what exists, how it is connected, who can reach it, and what is or is not enforced. This is an implementation inventory, not a target architecture or a recommendation to publish operational records.

## 1. Executive result

The repository implements a generic SanityPress content site and editorial Studio, plus a registered set of Unami Sports operational schemas. Generic pages and blog content can be published publicly through the site. A separate public sports directory now queries a restricted projection of active, explicitly published team profiles and appropriately approved fixtures, events and competitions.

**Current public boundary**

- Public: published `page` and `blog.post` content; the `/sports`, `/teams`, `/teams/{slug}`, `/fixtures`, `/events` and `/competitions` directories; the public sports navigation and sitemap entries.
- Studio-only by public-app code path: player, pilot, training, support, stakeholder, customization, governance, commercial, resource and talent documents; internal readiness/ownership data and all unprojected fields.
- Selectively public: team profile fields and listing-safe fixture/event/competition fields only when their GROQ filters pass. The queries use published perspective, exclude demo records, and project an explicit field allow-list.
- Public by manual editorial choice: information copied or rewritten into ordinary `page`/`blog.post` content. This does not publish the source operational document and is not a synchronized view.
- Not implemented: public player profiles, logged-in team surfaces, authentication/authorization, or access-controlled sports APIs.

**Safety conclusion:** do not make every record public just to make every capability reachable. Player data (including youth/consent fields), support requests, talent pathway records, governance drafts, commercial relationships, resource/budget information, and readiness notes remain operational records. Selected publication flags and readiness fields are now consumed by public queries, but they do not enforce document authorization or prove that approvals were genuinely obtained. Public queries expose a limited projection and exclude demos; editors still need to review content before enabling publication.

No production Sanity dataset, deployed project permissions, environment values, or external endpoint configuration was inspected. Conclusions about deployed roles, content, and service behavior are limited accordingly.

## 2. Status vocabulary

| Status             | Meaning in this report                                                                                                                                 |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **WIRED — PUBLIC** | A public route/query/component currently renders this capability from published CMS content.                                                           |
| **WIRED — STUDIO** | The schema is registered and/or exposed in Studio, but does not thereby become a public feature.                                                       |
| **PARTIAL**        | Some pieces exist, but the end-to-end workflow, route, persistence, enforcement, or integration is absent.                                             |
| **FLAG ONLY**      | A field or validation describes a gate, approval, ownership, consent, or publication choice but is not a runtime access-control/publication mechanism. |
| **DEMO ONLY**      | Code seeds illustrative records; this is not evidence of a live service or operational workflow.                                                       |
| **NOT FOUND**      | No implementation was found in the inspected repository.                                                                                               |

For each map row, the named actors are inferred from schema/UI labels and the public visitor/editor surfaces. They are not evidence that authenticated roles exist.

## 4. Document model and relationship map

### 4.1 Generic content model

Registered generic documents are `site`, `skill`, `page`, `global-module`, `blog.post`, `blog.category`, `redirect`, `form`, `announcement`, `logo`, `navigation`, `person`, and `quote`. Generic objects include `cta`, `link`, `link.list`, `megamenu`, `metadata`, `module-attributes`, `sidebar`, and `table`. Module schemas are listed in §5.

Key links:

- `site` → announcement, header/footer/bottom/social navigation, logo, CTAs.
- `page` → embedded modules, `metadata.slug`, optional curated markdown.
- `blog.post` → author (`person`), categories, Portable Text blocks/media/CTAs, optional markdown.
- navigation/link structures → internal `page` references or external URLs.
- page/post/global module data → reusable references such as forms, people, logos and quotes through module-specific GROQ fragments.
- `redirect` → internal page or external destination.

`person` documents may be exposed through published blog bylines or person-list modules. They do not gain an independent public route solely by existing.

## 7. Studio editorial structure and workflow reality

`src/sanity/structure.ts` groups editing surfaces as Global, Pages, Blog, Navigation, References, Club operations, Programme operations, Competition operations, Foundation stewardship, Finance and partnerships, Restricted pathways, and Drafts. Schema validation includes gates for pilot stages, competition states, event listing/status, commercial status, player public-profile flag and talent-pathway progression. These checks validate document values in the schema-driven editing workflow. They do not authenticate the person setting them, verify an external approval or consent event, restrict queries, trigger a task, provide audit-grade approval evidence, or create public rendering logic.

The config includes the Sanity Structure and Presentation tools, dashboard widgets (project info/users and Vercel), Vision, Code Input, Media, Assist and Portable Text plugins. Their availability is established by config; project account policies and deployed user roles are not.

## 9. Authority, ownership and privacy boundary

1. Sports ownership/authority fields are strings/enums and labels; schema descriptions repeatedly state they do not enforce Sanity document access.
2. No repository-defined sports authentication, session identity, team membership, RBAC middleware, per-team query filter, row-level policy, or sports API handler was found.
3. Sanity project-level user roles may exist outside this repository; they were not verifiable and should not be inferred from the Studio UI.
4. Validation predicates operate on the document shape and selected field values. A “true” boolean does not prove who approved, when, against which evidence, or whether the required process occurred.
5. Selected public flags and readiness values are consumed by public queries for teams, fixtures, events and competitions. This is publication filtering, not document access control or evidence that the approval process really occurred.
6. Public sports queries are restricted to published perspective, exclude demo records, require status/readiness/team conditions, and project explicit fields. Free-text operational details, player data, venue fields from fixtures, financial data, and internal workflow documents are not selected.
7. The absence of a public route for operational types is a code-path fact, not a guarantee that underlying Sanity datasets/assets are private from all other clients. Verify deployed project/dataset/API permissions separately before placing sensitive information in CMS.

## 11. What can safely surface publicly using the current implementation

The current implementation can surface:

- public team profiles and eligible fixtures/events/competitions through the dedicated routes and restricted projections;
- editor-authored public descriptions of the programme, teams, events, resources or partnerships as ordinary generic page/blog content;
- generic CTA/contact pages where the configured external endpoint is independently reviewed and functional;
- generic published content through page/blog routes and its supported metadata/discovery outputs.

The current implementation does **not** surface raw sports documents. The report therefore treats player, support, talent, governance, finance/resource, commercial, pilot-readiness, fixture venue/report and other operational details as non-public. The query projections omit these fields; events include only the separately labelled `publicVenueName`. “Published” in Sanity, setting a flag, or passing schema validation is not equivalent to actual authority, safe content review, or access control.
